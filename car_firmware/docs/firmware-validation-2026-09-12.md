# 2026-09-12 小车固件验证与修复

## 结论与测试条件

本次确认重构版存在影响启动、姿态计算和在线调参的回退，已修复并烧录上板。
修复版通过主机回归、同板 main 对照、重复软复位、运行周期观测、板上命令处理和
IMU 故障停机检查。结论限定为固件运行与控制计算；小车固定在支架上，轮电机和
舵机线均未连接，尚未验证实际机械平衡、反馈方向、动态抗扰和 PID 整定效果。

- 当前分支起点：`feature/SoftEngine`，`810b9a8`。
- 对照基线：`main`，`9b58e9e2c5841b2cead52b57b195567b3c94cd3d`；已通过
  `git ls-remote origin refs/heads/main` 核实与远程一致。
- 编译器：Arm GNU 14.2.1；目标 STM32F411 / Cortex-M4F。
- 主机测试编译器：MinGW GCC 16.1.0。
- 探头最终识别为 ST-Link V2J48M35；使用 OpenOCD 0.12 HLA，100 kHz 调试、
  1800 kHz 写入。Vref 仍误报约 0.59 V，但 CPU 识别、读写与镜像校验成功。
- 首次在低速写入时出现 Flash 算法超时，复位后改为 1800 kHz 写入成功，所有
  后续镜像均完成校验。未改写 ST-Link 固件、MCU option bytes 或读保护设置。

## 确认并修复的问题

| 问题 | 修复前重构版 | 本次修复 |
| --- | --- | --- |
| VQF 初始化 | Release/RelWithDebInfo 恢复 `-Ofast`，丢失 main 的修复 | 恢复 `-O3 -fno-fast-math`，同步 CMake 模板并恢复 VQF 编译保护 |
| 开机门控 | 硬件初始化成功后立即算轮输出，无稳定姿态等待 | 恢复连续 50 个 10 ms 稳定样本解锁；失稳取消解锁、清除 PID 历史 |
| 重心调节 | `anglebias` 仅保存，实际计算被固定腿高多项式覆盖 | 默认 9.5° 的最小腿高基准，加上 main 的相对腿高补偿 |
| 腿高校准 | 从 0 mm 初值计算，且使用 `(left + left)/2` | 从 44.5 mm 初始化，使用当前已限幅的左右腿目标平均值 |
| 姿态 Kp | `anglepid -p` 被每周期腿高增益覆盖 | `-p` 切换到持久手动 Kp，`-auto` 恢复原默认腿高增益 |
| PID 首帧 | 对第一次测量与零求差，产生微分冲击 | 首帧不计算测量微分；复位后同样处理 |
| 横滚 Kd | 命令不接受、控制任务固定传 0，纯 D 被提前返回 | 支持 `rollpid -d`，三项均生效；关闭三项时清空增量历史 |
| 运行诊断 | 缺少平衡解锁、实际 PWM 和采样周期信息 | 增加 `controlstate`，支持参数及实际重心/Kp 查询 |
| OpenOCD 配置 | 本机缺 `stlink-hla.cfg`，标准配置 transport 名不匹配 | 兼容本机 0.12 和新版本接口脚本命名 |
| OpenOCD 运行中校验 | 默认算法工作区与应用 RAM 重叠，目标 CRC 可覆盖状态/参数 | 启用工作区备份；写入/目标校验后复位，最终改用 Flash 读回后主机比较 |

保留重构版的显式硬件初始化、任务拆分、共享状态快照、初始化失败门控和运行故障
锁存。默认自动 Kp、重心公式、10/50 ms 控制节拍与 main 保持一致。

## 软件验证

- 修改前已有 28 项测试全部通过；它们没有覆盖被覆盖的 Kp/重心和 VQF 启动。
- 用恢复自 main 的 VQF 测试，在未修复的 `-Ofast` 构建中复现：水平静止输入，
  第 0 帧横滚为 180°，期望为 0°。
- 修复后主机 Debug、Release 各 **31/31** 项通过。
- VQF 回归包含四种姿态，每种 1000 帧，覆盖首帧及滤波器预热退出。
- 新增集成回归运行真实命令任务与运动任务，用测试硬件适配器输入数据，逐项验证
  四组 PID 的 P/I/D 共 12 个解析到输出的阶跃响应；覆盖手动/自动 Kp、改变腿高、
  重心基准持续生效、双腿平均值、非法数值、瞬态 IMU 失败、重新解锁及故障锁存。
- 固件 Debug、Release、RelWithDebInfo 均构建成功。Release 与带调试信息的优化
  构建生成完全相同的 `.bin`。

## 同一块板上的实测

依次烧录了当前分支修改前、main、本次修复版的已知镜像，每次均校验后再观察。
进入任务前 GDB 显示的源代码/变量可能属于上一镜像，不用作对比证据；以下取
烧录校验及复位后的数据。

| 观测 | 修改前重构版 | main | 修复版 |
| --- | --- | --- | --- |
| 硬件/任务启动 | 初始化成功、控制开启 | 控制任务运行 | `ready`，硬件尝试 `0xFF`，硬件/任务失败均 0 |
| 静止横滚 | 两次读取约 `0.013°` / `-179.987°` | 约 `-0.76°` 到 `-0.59°` | 约 `-0.77°` 到 `-0.61°` |
| 约 2 s 的俯仰 | VQF 已异常，不作为真实姿态 | `-13.970°` | `-13.967°` |
| 约 2 s 的实际 bias / Kp | `12.712 / 80.45` | `8.043 / 71.736` | `8.025 / 71.760` |
| 约 2 s 的双轮 PWM | `1000 / 1000` | `425 / 425` | `429 / 429` |
| 约 12 s 的双轮 PWM | 未继续作为基准 | `527 / 527` | `520 / 520` |
| 约 12 s 的实际 bias / Kp | — | `6.60252 / 75.35` | `6.60252 / 75.35` |
| 处理器 CFSR / HFSR | 0 / 0；无硬异常仍可能算错 | 0 / 0 | 0 / 0 |

上述 PWM 差值受到两次采样时刻及 IMU 小幅变化影响，属于支架上固定输入条件的
对照，不能替代接通执行器后的动态比较。

### 启动、持续运行和资源

- 五次软复位均成功：复位后约 250 ms 的读取仍为 `armed=false`、双轮 PWM 0；
  约 650 ms 的读取均已 `armed=true`，IMU 有效，硬件/任务失败位均为 0。
  时间包含 OpenOCD 指令和读取开销；门控的精确 50 样本行为另外由主机测试验证。
- 独立持续运行段最终记录 6071 次姿态循环、系统 tick 60743；历史最大采样间隔
  10 tick，`deadline_misses=0`。观测中未见 HardFault 或控制故障。
- 调参前另一次未复位运行达到约 300 s / 30000 次循环，仍为 10 tick 最大间隔、
  0 超期；期间有调试器连接，不能称为无调试干预的长期耐久测试。
- 稳态可用 FreeRTOS heap 为 11032 B，历史最低 8552 B。
- 从任务栈填充值估算本次运行的最低剩余空间：Heartbeat 636 B、CommandService
  7040 B、ServoControl 668 B、MotionControl 8464 B、ButtonA0 376 B。
  这些是本次负载的观测值，未覆盖 UART/nRF 满负荷或所有中断嵌套。

### 板上调参和故障测试

ST-Link VCP COM6 可打开，但发送 `ping` 未收到回应。因此在暂停 CPU 时，将十条
调参文本写入车端命令队列，并设置命令任务的通知状态，让真实任务在自身上下文
处理；没有替换生产算法，也没有直接改写 PID 的目标参数。本测试覆盖队列后的
解析、参数快照、控制计算与定时器写入，未覆盖物理 UART/nRF 收包。

- `anglepid -p 80` 后，`R 0 0 0 61.5` 和 `legheight 78.5` 均不能覆盖 Kp=80。
- `anglebias 10.5`：61.5 mm 时实际 bias=7.60251951°，78.5 mm 时为 10.6353188°。
- `anglepid -p nan` 被拒绝，原参数保留。
- `anglepid -auto` 恢复 78.5 mm 对应的 Kp=80.4500046。
- 姿态 P/I/D 全部为 0 时，实际反馈 PWM 和 TIM1 CCR1/CCR2 都为 0；重新设置
  Kp=80 后输出恢复，证明修改参与了真实硬件控制计算。
- 用 SWD 将 HAL I2C 状态置为 BUSY，模拟读失败；70 ms 后观察到 `runtime_fault`、
  `control=0`、轮 PWM=0、舵机 CCR1/CCR2=0、TIM9 CCER=0、轮方向脚为低。
- 恢复 I2C READY 后观察 500 ms，故障仍锁存，输出继续关闭。随后复位，默认
  参数、初始化和稳定姿态解锁均恢复；最终镜像再次校验通过。

后续复核发现，OpenOCD 默认目标算法工作区为 `0x20000000`，且不备份；在运行
状态下调用 `verify_image` 会在这里写入 CRC 代码，覆盖 `g_app_system_state` 和
参数。数据中出现了 CRC 多项式 `0x04c11db7`，Flash 镜像仍正确，复位后恢复。
该现象来自调试步骤，不能作为固件自行发生内存破坏的证据。

已在两份 ST-Link 配置中启用工作区备份；同时确认备份本身并不能消除目标算法
运行期间对任务的干扰，所以最后采用直接读回 Flash、在主机逐字节比较的方法。
所有编程/目标算法校验结束后均复位再观察业务状态；后续正常运行检查不执行
目标 CRC 算法。

最终只读复核记录：`ready`、硬件/任务失败位均 0、`armed=true`、`imu_valid=true`，
40369 次循环、tick 403723、最大间隔 10 tick、0 超期。之后恢复 MCU 运行并关闭
本次 OpenOCD 服务，未留下暂停或临时调参。

## 使用方法

保持原有 32 字节 ASCII 无线命令格式。示例每次发送一条：

```text
anglebias 10.5
anglepid -p 80
anglepid -i 0
anglepid -d 55
velocitypid -p 0.05
differpid -i 0.001
rollpid -d 0
```

`anglepid -auto` 恢复自动 Kp。发送不带参数的 `anglepid`、`velocitypid`、
`differpid`、`rollpid` 或 `anglebias` 查询；`status` 和 `controlstate` 查看门控
及控制状态。参数仅在 RAM 保留，重新上电恢复默认值。

## 尚需实物验证的边界

- 修复版的五次软复位已验证；最后请求的物理断电重启尚未收到完成确认，未将其
  计入冷启动测试结果。后续应在不执行额外软件复位的情况下连接并读取启动状态。
- 轮子、舵机未接线，编码器 RPM 没有主动运动输入；无法验证闭环稳定性、
  动态平衡、方向、舵机行程和实际 PID 整定。
- 断开舵机时，横滚积分会使单侧腿目标逐步到达限位；main 与修复版均观察到，
  本次只能确认目标和输出有界，不能确认真实闭环收敛。
- main 与修复版都存在约 4.6°/s 的静止 yaw 漂移。当前差速环使用轮速差，不使用
  yaw；陀螺零偏仍沿用原固定值，本次未另行标定。后续整机调试应检查传感器零偏。
- 未实测真实无线调参、满负荷通信、移动输入和长时间机械运行。
